# Agent Failure Modes

A note on how agent pipelines fail, as of October 2026: the published failure taxonomies (MAST and newer ones) with their measured frequencies, long-running agent failures, tool and provider failures with incident dates, retry and cost failures, parallelism, flaky tests, silent failures and public incidents, ending in one big table of failure, symptom, detection, mitigation and source.

## In one paragraph

Failures in agent pipelines cluster by layer, not by engine. The model and loop layer produces premature termination, step repetition and long-horizon decay; the tool layer produces success signals that lie (an SDK result that says success while the last request failed, an exit code 0 with zero tests run); the provider layer produces outages, silent degradation and rate limits (one provider's public status feed, which returns its 50 most recent incidents, covered only 72 days on 2026-10-12); the cost layer produces retry storms and uncapped loops; the coordination layer produces merge conflicts and contagion; and the operations layer produces silent failures that mostly humans find (about 70% in one production study), lost traces and over-scoped credentials. The measured frequencies are specific to their datasets, but they agree on shape: verification failures are a first-class category (6.2% to 9.1% of traces per mode in MAST), repetition is the most common single mode (15.7%), a reliability collapse arrives within about sixteen dependent steps on a tool-use task, and public incident write-ups blame plumbing and permissions far more often than hallucination. Most mitigations are code, not prompts: caps, classified retries, verified state, fresh context per phase and credentials with a small blast radius. That is also why changing the orchestrator changes which failures are loud, not which failures happen.

## 2. Taxonomies and measured frequencies

### 2.1 MAST, the base taxonomy

[Why Do Multi-Agent LLM Systems Fail?](https://arxiv.org/abs/2503.13657) (UC Berkeley, 2025-03-17) annotated 1,642 execution traces from 7 multi-agent frameworks (GPT-4 and Claude families) and sorted the failures into 14 modes under three categories: system design (FM-1.x), inter-agent misalignment (FM-2.x) and task verification (FM-3.x). The taxonomy was built on an initial 150 traces and reached inter-annotator kappa 0.88. It ships an LLM-as-judge annotator and a public dataset ([MAST-Data on Hugging Face](https://huggingface.co/datasets/mcemri/MAST-Data); [code](https://github.com/multi-agent-systems-failure-taxonomy/MAST), no LICENSE file found at the repo root). The percentages below are the share of the 1,642 traces showing each mode; a trace can show several, and the paper gives no combined share per category. The table lists eight of the fourteen modes; the other six are in the paper.

| Code | Mode | Prevalence |
|---|---|---|
| FM-1.1 | Disobey task specification | 11.8% |
| FM-1.3 | Step repetition | 15.7% |
| FM-1.4 | Context loss | 2.80% |
| FM-1.5 | Unaware of termination conditions | 12.4% |
| FM-2.6 | Reasoning-action mismatch | 13.2% |
| FM-3.1 | Premature termination | 6.20% |
| FM-3.2 | No or incomplete verification | 8.20% |
| FM-3.3 | Incorrect verification | 9.10% |

Two measured interventions: improving agent role specifications alone gave +9.4% task success for ChatDev with GPT-4o, and adding a high-level objective verification step gave +15.6% on ProgramDev. The authors note that many existing verifiers do only superficial checks, such as whether code compiles; their example under FM-3.2 is a ChatDev-generated chess program that "passes superficial checks (e.g., code compilation) but contains runtime bugs".

### 2.3 What the taxonomies agree on

- **Verification is a first-class category.** MAST's three verification modes sum to a large share of traces, and TestJack's 34.4% says the same from the outcome side. See [Reward Hacking and Verification](reward-hacking-and-verification.md).
- **Closed loops absorb faults that kill linear pipelines** (MAS-FIRE), which supports gated and loop phases over a straight chain.
- **Production agents stay short and supervised.** In the [MAP study](https://arxiv.org/abs/2512.04123) (20 case studies and 306 surveyed practitioners, filtered to 86 deployed-system responses, April to November 2025) 68% of deployed agents execute at most 10 steps before human intervention, 70% prompt off-the-shelf models, 74% rely primarily on human evaluation, and reliability is the top challenge. In Inngest's vendor survey of 130 engineers, [20% of AI teams spend 26-50% of engineering time on reliability work](https://www.inngest.com/blog/ai-in-production-report-2026) (twice the 10% rate of non-AI teams) and observability is seen as the number one unsolved problem.

## 3. Long-running agents: horizon, drift and context

**Horizon math.** [How Fast Do Agents Rot?](https://arxiv.org/abs/2609.01660) (2026-08-31, single author) analyzed 10,664 trajectories across nine models (six open, 1.2B to 671B parameters, and three deployed proprietary systems), four task families and five horizons. Task success follows a geometric law in the number of dependent steps, governed by a per-step reliability that saturates below 1. On the agentic tool-use task every model fell "from near-perfect success to near zero within sixteen steps". In the streaming families, bounding the context window made decay worse (logit slope per horizon doubling -0.69 compressed against -0.44 natural, p=3x10^-6; -0.40 padded, not different from natural), so compaction is not a fix for step count. The fitted law projects, but does not measure, success of 0.42 at GAIA-length horizons (8 steps), 0.30 at SWE-bench length (30 steps) and 0.24 at hundred-step production horizons. Reading for a pipeline: short gated phases reset the horizon, while one long loop compounds per-step error.

**Drift.** [Capable but Unreliable](https://arxiv.org/abs/2602.19008) (2026-02-22) held model and task fixed on Toolathlon (22 frontier models x 108 tasks x 3 runs, 2,286 pairs, 515 with mixed outcomes, 488 in the headline analysis) and found that successful runs adhere more to the canonical tool-call path than failed runs of the same model and task (+0.060 Jaccard, p<0.0001), and that the drift is self-reinforcing: each off-canonical call raises the chance the next is off-canonical by 22.7 percentage points. The estimated effect of restarting the bottom tercile of runs at 75% completion is +8.8 pp among intervened runs, which is the case for LOOP phases with an iteration cap and a restart from the last artifact.

**Uncertainty arrives late.** [Last Step Matters](https://arxiv.org/abs/2608.29685) (2026-08-30) tested deep-research agents, not coding agents: final-step verbal confidence reached mean AUROC 0.85 across 15 model-benchmark combinations, but no signal exceeded 0.60 at 50% of the trajectory and all stayed under 0.70 even at 90%, because agents switch paths mid-run. The recommendation is to decide at the gate, not mid-flight; applying it to gated SDLC phases is an inference, and it sits awkwardly with the Toolathlon monitor that acts at 75%.

**Context rot.** Anthropic frames context as a finite ["attention budget"](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents): as tokens grow, recall of the context decreases (rooted in n-squared pairwise attention). Chroma's [July 2025 study](https://www.trychroma.com/research/context-rot) across 18 LLMs found performance "degrades as input length increases, often in surprising and non-uniform ways", with near-perfect needle-in-a-haystack scores hiding degradation on semantic and distractor tasks. A [September 2026 vendor-blog test](https://www.boolean.ai/blog/context-rot-quantified) of a 20-task terminal-bench v4 subset prefilled at 0k, 250k and 500k tokens saw GPT-5.6 Sol fall from a 31% to a 24% pass rate at 250k (persisting at 500k), while Claude Opus 5 was flat under unrelated context ("within evaluation noise") but fell from 50% to 40% when the context was related to the task. Small sample; Claude Code defaults to 1M context while Codex limits to 400k by default (reconfigured to 1M for the test). Supports a fresh context per phase.

**Compaction and harness bugs.** An agent told "don't action until I tell you to" reportedly lost the instruction when a large inbox triggered compaction (the user's own diagnosis; [PCMag](https://au.pcmag.com/ai/116091/meta-security-researchers-ai-agent-accidentally-deleted-her-emails)), and Anthropic's own April 2026 harness bug cleared prior thinking on every turn instead of once, passing multiple human and automated reviews, unit and end-to-end tests, automated verification and dogfooding before taking over a week to root-cause ([postmortem](https://www.anthropic.com/engineering/april-23-postmortem)). Constraints that matter should live in code.

## 4. Tool errors and false success signals

The big-table rows C1 to C5 carry the main facts. Details worth keeping:

- **The path, not the model.** The [intent-execution study](https://arxiv.org/abs/2610.04375) measured 47,828 shell calls in a Windows corpus (Claude Code and Codex through Git Bash and PowerShell 5.1; 261 sessions, 6 developers of one company, 11 weeks): Claude Code's Bash tool changed 12.0% of the 7,491 calls carrying code, escape sequences or long text; for 80.7% of calls with altered backslashes (535 of 663) the wrong action ran without any reported error; all 10 measured harnesses changed a call; on IEC-Bench the path raises token cost per passed task 2.4x (up to 12.3x). The corpus is Windows-heavy, so read it as a warning to test your own hops, not as a Linux-runner statistic. The companion repo is MIT-licensed.
- **Narrated tool calls and tools that exit 0.** Collected in the [Foojay/NLJUG article](https://nljug.org/foojay/commit-created-but-it-isnt-why-the-agents-word-needs-external-verification-and-what-the-mistake-costs/) (claude-code #63870, vscode-cmake-tools #4915, codex #41626; the issue pages themselves could not be opened here).

### 5.3 What to do about them

Provider incidents are weather: frequent, short and sometimes coincident. The error taxonomy matters more than the dashboard. The [Claude API errors page](https://platform.claude.com/docs/en/api/errors) defines 429 `rate_limit_error`, 500 `api_error`, 504 `timeout_error` and 529 `overloaded_error`; the official SDK retries transient failures "twice by default" with exponential backoff, honoring `retry-after`; a streaming error "can occur after the API returns a 200 response"; and "A tier spend-cap 429 has no retry-after header and keeps failing until access resumes" (a 400 for organization or workspace spend limits you set, except Claude Code workspace limits, which can return 429). Rate limits use a token bucket. A durable engine lets a long run wait out an outage with heartbeats instead of restarting and paying twice; multi-provider failover has its own failure (D4) and a fallback with strict limits can be hit by a retry storm.

### 6.2 What the catalogs say

The Token Budgets paper (2026-06-02, 21 frameworks, each of the 63 confirmed incidents backed by a quoted GitHub issue) finds retry loops the largest cluster and multi-agent delegation fan-out where caps get bypassed: the fan-out race appears in 11 incidents, and the same pattern under asyncio overshoots in 30 of 30 runs in the author's experiment against 0 of 30 for three disciplined alternatives; on single-agent workloads a 4-line Python counter matches the 1,180-line Rust crate at 0/30 overshoot. Only the cluster counts are quoted here because the eight-cluster partition was single-rater (kappa 0.837 applies to a four-class classification).

### 6.3 Cost stories, labeled by confidence

## 7. Parallel agents: conflicts and contagion

- **Conflicts with the base.** [AgenticFlict](https://arxiv.org/abs/2604.03551) (2026-04-04) simulated merges for 107,026 of 142,652 agentic PRs (59,412 repositories, five coding agents): 29,609 conflicted (27.67%) across 336,380 conflict regions. These are conflicts against the target branch at simulation time, not specifically between parallel agents, so do not present it as a fan-out statistic.
- **Between agents.** On AIDev-pop (33,596 PRs, 2,807 repositories) [40.2% of repositories](https://arxiv.org/abs/2607.04697) (1,129) had co-active agent PR pairs; the textual conflict rate was 41.7% for cross-agent pairs (48 of 115 evaluable) against 19.8% for same-agent pairs (119 of 601); 84.4% of conflicted files were source code and about 42% of conflicts were structural (modify/delete or add/add). The comparison rests on a few hundred evaluated pairs.
- **Plan scopes, then merge in order.** [NP-Bench](https://arxiv.org/abs/2610.07261) (single author, own benchmark of 9 scenarios) reports clean integration in 1 of 9 with no coordination, 4 of 9 with reactive detection and 9 of 9 with an up-front scheduling planner (merge conflicts 13, 12 and 0); in a live contract-change test the clean-integration rate went from 0 to 1.0 on Claude Opus 4.8 and 0.6 on Claude Haiku 4.5, and none of five agents strayed from assigned scopes. Its planner ships inside Nerveplane (Functional Source License 1.1 with an MIT future license, so source-available). The pattern, disjoint scopes and ordered merges decided by the controller, is the useful part.
- **Agent-decided concurrency** is its own failure source: the Codex, Claude Code and Kimi Code study found dynamic spawning helps most on long-horizon tasks and catalogs 13 concurrency-specific failure modes. A declarative fan-out in a phase registry avoids most of them.

## 8. Flaky tests and flaky checks

[On the Flakiness of LLM-Generated Tests](https://arxiv.org/abs/2601.08998) (2026-01-13) studied four database systems (SAP HANA, DuckDB, MySQL, SQLite) with GPT-4o and Mistral-Large-Instruct-2407: LLM-generated tests were slightly flakier than existing ones, the most common root cause was an unordered collection (72 of 115 flaky tests, 63%), and both models copied flakiness from tests in their prompt context (more so in the closed-source system). The models are 2024-vintage. The cost for a pipeline is this page's inference: in an iterate-until-green loop a flaky test makes the agent chase ghosts and burn CI rounds, which is why fix-round caps exist. Related effects: with flaky tools a final response "may present unverified work as completed" ([GPT-5.6 system card](https://deploymentsafety.openai.com/gpt-5-6), vendor); LLM-judged checks flake too (G3); and infrastructure noise alone moved a benchmark 6 points ([Anthropic](https://www.anthropic.com/engineering/infrastructure-noise)). See [Evals for Agentic Pipelines](evals-for-agentic-pipelines.md).

## 9. Silent failures and observability loss

- **Fail-plausible.** [When Errors Become Narratives](https://arxiv.org/abs/2606.14589) (2026-06-12, single author) is eight weeks of postmortems on one production runtime (in service since March 2026: about 40 scheduled jobs, 8 LLM providers, 4,286 unit tests in 121 suites, 827 declarative governance checks; a personal assistant on a single macOS host with one operator): 22 incidents with full postmortems, a failure whose error signal never reaches a human in actionable form at least 28 times, about 70% of silent failures caught by a human viewing the output, and, in a retrospective audit of 15 incidents, 0% ex-ante prevention but 87% ex-post regression blocking, with incident latency from 13 hours to 60 days. The worst class, "fail-plausible", is where the LLM turns an internal error into fluent output.
- **A mechanized observer finds little.** [Mechanizing the User's Eye](https://arxiv.org/abs/2610.05981) (2026-10-05) built five deterministic signals escalating to an LLM judge that must cite verbatim evidence. Of 24 labeled postmortems, 16 were structurally invisible to any content-reading observer; the deterministic layer detected 6 of 6 regressions offline with 0 of 4 false positives, but held-out recall on novel patterns was 0 of 4; a 26-day shadow window (2026-06-30 to 07-25) ran clean and a 12-day enforcing window fired zero verdicts; the observer itself produced ten silent failures during development.
- **Diagnosis.** On TRAIL the best 2025 model scored 11%. [AgentRx](https://arxiv.org/abs/2602.02475) (170 annotated trajectories across 11 task settings) localizes the critical failure step by synthesizing constraints and checking them step by step, improving step localization by 75% on average. A 2026 paper reports one-shot LLM judges settle on a plausible diagnosis early and that an iterative Continual Search raised Opus-4.8's root-cause F1 on long traces from 0.471 to 0.608 on its own benchmark ([arXiv](https://arxiv.org/abs/2609.13463)). That structured per-phase artifacts beat one giant trace for a judge is this page's inference.

## 12. A ten-line control list that works on any engine

1. Cap turns and budget on every phase (E3); escalate by default (A1).
2. Classify errors before retrying; one retry layer; cap attempts on LLM Activities (D1, D2, E1, E2).
3. Check `is_error`, `api_error_status` and `terminal_reason`; verify artifacts on disk (C1, C3).
4. Fresh context per phase; artifacts, not transcripts, between phases (A6, B1).
5. Constraints in code, never only in the prompt (B2, I2).
6. Validate reused artifacts and every fan-out child in code (E5, F3).
7. Plan scopes and merge order in the controller; push late (F1, F2).
8. Run CI locally until green, then push once (G2).
9. A dead man's switch on traces and an age alarm on escalations (H3, H5).
10. Least-privilege, short-lived credentials and branch protection (I1, I3).

## Gap-fill additions (2026-10-12)

- **A spend cap can itself be the outage (section 5).** [Claude Status: Issue with spend limits](https://status.claude.com/incidents/vmys9qn874h4) (2026-10-07, 21:23 UTC): "some organizations to be incorrectly paused for having reached their spend limit, resulting in refused requests on the Claude API, Claude.ai, Claude Code, Claude Security, and Claude Cowork". Resolved, rated impact "none" in the incidents feed, and the newest entry in it on 2026-10-12. It is the other side of the hard-budget-cap advice: a controller should tell "refused for budget" from "provider down" and never retry the first as if it were transient (D2).
- **A harness can make the model report a wrong failure (section 4).** [claude-agent-sdk-python CHANGELOG](https://raw.githubusercontent.com/anthropics/claude-agent-sdk-python/HEAD/CHANGELOG.md), 0.2.160: stdin was closed too early when a background subagent finished just before the turn's result arrived, so follow-up turns failed with "Stream closed" and "the model would report the tool as refused". A bounded wait ceiling (`CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS`, default 10 minutes) now prevents indefinite hangs. A false signal can come from the harness, not the model: check the pinned SDK version against the changelog.
- **Status-feed window.** For the "50 in 72 days" row: the incidents endpoint returns at most its 50 most recent items (page 2 returns the same 50), so the window start is set by the cap and slides as new incidents post.
