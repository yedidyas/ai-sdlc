# Engineering Case Studies

## How to read this note

- **Basis column.** "Primary" means the company's own engineering post or paper. "Secondary" means press, a podcast or a summary of a talk. "Vendor story" means a case study hosted by a vendor of the tool it features.
- **Numbers.** All volumes and savings are company-reported unless stated; none is independently audited. Cost per PR or per run is almost never published (see [Cost Economics](cost-economics.md)); for what the measured research says, see [Productivity Evidence](productivity-evidence.md).
- **Dates.** The post date is given with each case. Cases are as of October 12, 2026.

## 2. Detailed cases

### 2.1 Stripe: Minions

- **What they built.** Fully unattended agents that start from a Slack thread (or the docs, feature-flag and ticketing UIs) and end in a CI-passing PR for human review ([Part 1](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents), Feb 9, 2026; [Part 2](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2), Feb 19, 2026).
- **Architecture.** "Blueprints", workflows defined in code that mix deterministic nodes (run configured linters, push changes) with agent nodes (implement the task, fix CI), on a fork of Block's goose. Conditional rule files are synced across Cursor, Claude Code and Minions, and each agent gets a curated subset of Toolshed MCP tools. A [ByteByteGo write-up](https://blog.bytebytego.com/p/how-stripes-minions-ship-1300-prs) (Mar 16, 2026) summarizes why: making the deterministic steps code "saves tokens, reduces errors, and guarantees that critical steps happen every single time".
- **Orchestration choice.** Its own blueprint layer. Stripe does not disclose a durable execution engine behind it or a cost per run.
- **Sandbox.** Pre-warmed devboxes that spin up in 10 seconds, isolated from production and the internet, so no human permission checks are needed.
- **Scale and results.** More than a thousand PRs merged each week (the ByteByteGo headline says 1,300).
- **Admitted limits.** At most two rounds of CI: after the second push the branch goes back to the human, because more rounds "cost more tokens and compute without proportional improvement".

### 2.2 Spotify: Honk and Fleetshift

- **What they built.** An LLM agent added to Fleet Management, where prompts replace deterministic AST and regex migration scripts while targeting, PR opening, review and merge stay the same ([Part 1](https://engineering.atspotify.com/2025/11/spotifys-background-coding-agent-part-1), Nov 2025). Around half of Spotify's PRs have been automated since mid-2024.
- **Architecture.** A small internal CLI wraps the agent, runs formatters and linters over local MCP, uses an LLM judge on the diff and traces to MLflow. The homegrown loop (10 turns per session, three session retries) broke on multi-file changes, so Spotify moved to Claude Code, later through the Agent SDK ([Part 2](https://engineering.atspotify.com/2025/11/context-engineering-background-coding-agents-part-2)). The agent gets only a verify tool, a restricted git tool that never pushes, and allowlisted Bash; no code-search tools, because "the more tools you have, the more dimensions of unpredictability you introduce". Pushing code, Slack and even prompt authoring are handled by surrounding infrastructure ([Part 3](https://engineering.atspotify.com/2025/12/feedback-loops-background-coding-agents-part-3), Dec 2025).
- **Orchestration choice.** Fleetshift for targeting, scheduling and PR tracking, with Honk "wrapped inside our own harness and deployed in Kubernetes pods" ([Jun 3, 2026](https://engineering.atspotify.com/2026/6/code-with-claude-coding-is-no-longer-the-constraint)). Not a general durable engine.
- **Sandbox.** Kubernetes pods plus the restricted tool surface.
- **Scale and results.** 1,500+ merged agent PRs and 60-90% time savings (Nov 2025); 2.5M+ automated maintenance PRs, most auto-merged, over 99% of engineers using AI tools weekly, a 76% increase in PR frequency, and a Java migration across backend services in three days (Jun 2026); about 1,800 downstream data pipelines with 240 automated migration PRs, estimated at around 10 engineering weeks saved ([Part 4](https://engineering.atspotify.com/2026/4/background-coding-agents-dataset-migrations-honk-part-4), Apr 22, 2026). Merged changes more than doubled year over year in August 2026, about 8,100 to 17,000 ([Sep 16, 2026](https://engineering.atspotify.com/2026/9/ai-changed-how-spotify-builds-what-we-learned-and-fixed-about-quality-at-higher-velocity)).
- **Admitted failures.** Three failure modes, the worst being a PR that passes CI but is functionally wrong; a stop hook runs every verifier before a PR may open, and the judge vetoes about a quarter of sessions (the agent recovers half the time), but "we have yet to invest in evals for our judge". Scio migrations were dropped because a comprehensive prompt got unwieldy; SQL repos had no build-time tests, so the agent could not verify its work. An automated dependency upgrade passed checks and still failed in production; volume outgrew verification controls and PR size is creeping up.
- **Key points.** Verifiers behind one tool plus a stop hook; the veto-rate number as a lie-detector statistic; and the line "AI increased the capacity to produce change. The next constraint became our ability to verify it".

### 2.3 Ramp: Inspect, OCA, security agents, integrations

- **What they built.** Inspect, a background coding agent ([Jan 12, 2026](https://builders.ramp.com/post/why-we-built-our-background-agent)); OCA, an on-call assistant that investigates incidents and asks Inspect for fix PRs ([Sep 9, 2026](https://builders.ramp.com/post/how-we-built-oca-our-ai-on-call-assistant)); a security-agent experiment ([Feb 20, 2026](https://builders.ramp.com/post/100-vulnerabilities-patched-with-0-humans)); an integration factory ([Aug 14, 2026](https://builders.ramp.com/post/integrations-that-write-themselves)).
- **Architecture and orchestration.** Each Inspect session runs in a Modal sandbox VM with the full stack (Vite, Postgres, Temporal), using OpenCode as the agent and Cloudflare Durable Objects (one SQLite per session) for the API and state: a control plane that is not a workflow engine. OCA is different: Temporal manages the investigation workflow "so it can survive worker restarts and deploys". The security experiment fans detector agents out from a manager and has adversarial validators critique findings. The integration factory generates a per-call script once and runs it deterministically afterwards.
- **Scale and results.** About 30% of PRs from Inspect sessions; about 100 security issues found, validated and patched in a one-week experiment; integrations at under $15 each.
- **Admitted failures.** Early OCA models stopped at the first plausible explanation. Strict blocking hooks made agents retry blocked actions, so Ramp added six one-shot "detour" hooks that force self-checks before posting. The validators rejected 40% of initial findings, all later confirmed false positives by human review.
- **Key points.** Two orchestration shapes in one company (sessions versus durable workflows); "generate once, then deterministic"; the cost and value equations ([Ramp](https://builders.ramp.com/post/ai-spend-value)); the 40% rejection as a verification statistic.

### 2.4 Cursor: Cloud Agents on Temporal, and agents at scale

- **What they built.** Cloud Agents on Temporal Cloud, described in a [ZenML summary](https://www.zenml.io/llmops-database/building-and-operating-agentic-ai-coding-products-at-scale-with-temporal) of a Cursor talk (the talk itself and the summary's date were not found), plus a [Jan 14, 2026 post](https://cursor.com/blog/scaling-agents) on running hundreds of concurrent agents for weeks.
- **Architecture and orchestration.** A homegrown ECS runner system reached about 90% success ("essentially building a poor version of Temporal"); activity success on Temporal exceeds 99%. Activities write to content-addressable storage (S3, Redis streams) and restart "without replaying expensive model token sequences". The scaling experiments found that flat self-coordination with locks fails and a planner, worker and judge hierarchy works.
- **Scale and results.** About 50 million Temporal actions a day across over 7 million unique workflows; a browser experiment of over 1 million lines across 1,000 files in close to a week; a Solid-to-React migration of over three weeks with +266K and -193K edits.
- **Admitted failures.** Deploys produced a 90-minute wait for activities to drain and workflows bouncing between code versions (non-determinism errors); the fixes were shorter turn-scoped workflows with signal-with-start, a move from ECS to Kubernetes with Temporal's worker controller, and CI replay of sampled production histories. With locks, "twenty agents would slow down to the effective throughput of two or three"; an integrator role "created more bottlenecks than it solved"; "Opus 4.5 tends to stop earlier and take shortcuts when convenient"; "too little structure and agents conflict, duplicate work, and drift; too much structure creates fragility".

### 2.5 Uber: the Software Factory

- **What they built.** Managed agents across the lifecycle ([cost post](https://www.uber.com/us/en/blog/efficient-software-factory/), Aug 27, 2026), on an agent platform started in early 2025, with an Agent Registry, a Security Token Service minting single-hop short-lived JWTs anchored in SPIRE workload identities, an MCP Gateway covering more than 1,000 MCP servers and an AI Gateway ([identity post](https://www.uber.com/us/en/blog/solving-the-agent-identity-crisis/), May 21, 2026). A related [talk](https://youtu.be/17-YSUHo6Lk) is on the AI Engineer channel.
- **Orchestration.** Not disclosed; the post is about spend and identity.
- **Scale and results.** More than 70% of PRs attributed to local or cloud agents; over 3,600 agent skills and 30K skill executions a day; weekly active users 7x and weekly agentic requests 9.4x from February to August 2026; cost per 1,000 requests down almost 34% from its peak and cost per session down 52% from its June peak.
- **Admitted failures and tensions.** Fortune relays that Uber burned through its entire 2026 AI coding tools budget in four months ([May 22](https://fortune.com/2026/05/22/microsoft-ai-cost-problem-tokens-agents/)); its COO says the link between that spend and more useful features ["is not there yet"](https://fortune.com/2026/05/26/uber-coo-ai-spending-tokens-claude-code/) (May 26). The CEO figure in the same story is about 10% of committed code built by autonomous agents, a different measure from the post's PR attribution.
- **Key points.** The weaker-model default for subagents ("the most impactful lever"), compaction at 400K tokens, cost per merged PR and revert rate as named metrics, and the actor chain as the answer to "which agent opened this PR on whose behalf".

### 2.6 Block: BuilderBot and Moneybot

- **What they built.** BuilderBot, on the open-source goose framework: engineers tag it in Slack, it picks up Linear or Jira tickets, branches, opens a PR, watches CI and iterates ([The New Stack](https://thenewstack.io/how-block-manages-its-fleet-of-ai-coding-agents-from-slack/), Jun 17, 2026). Moneybot, an autohealing loop for production LLM failures at Cash App ([Block engineering](https://engineering.block.xyz/blog/autohealing-moneybot), Aug 28, 2026).
- **Architecture.** An orchestrating agent with six sub-agents (Reproducer, Diagnoser, Fixer, Verifier, Publisher, Review Addresser) reproduces failures with sampled evals, fixes them in isolated worktrees, verifies on disposable staging with the same sample size, and opens a fix PR plus the eval as a regression test.
- **Scale and results.** More than 200,000 operations a day and about 1,500 PRs a week, roughly 15% of all production changes across Block (press figures; BuilderBot stays internal). Moneybot: more than 40 verified fixes and more than 100 reported failures that no longer reproduce.
- **Admitted limits.** "In an LLM application, one green run proves very little": baselines use ten runs, resampling to twenty if the bug appears once. "Humans keep the irreversible actions, including merging pull requests and closing tickets"; "autonomy is most useful in the reversible parts of engineering".

### 2.7 Migrations: Airbnb, Google and Slack

- **Airbnb.** Modeled each of nearly 3.5K Enzyme test files as a state machine of validate-then-fix steps with retry loops that carry the latest errors in dynamic prompts (40K-100K tokens, up to 50 related files). 75% migrated in four hours, 97% after four days of "sample, tune, sweep", long-tail files retried 50 to 100 times, and the last 3% (under 100 files) fixed by hand in about another week. 1.5 years estimated, 6 weeks actual.
- **Google.** [An experience report](https://arxiv.org/abs/2501.06972) (Jan 2025) defines success as at least 50% end-to-end time saved (not percent of AI-written code) and notes humans had to revert some model changes, which led to LLM-driven verification; [the 12-month case study](https://arxiv.org/abs/2504.09691) counts 39 migrations by three developers, 595 changes with 93,574 edits, 74.45% of changes LLM-generated, and an estimated 50% time reduction. Deterministic targeting decides where to change; the LLM decides how.
- **Slack.** More than 15,000 Enzyme tests and more than 10,000 potential engineering hours; AST-only 45%, Claude 2.1 alone 40-60%, and an AST-plus-LLM hybrid (converted code, annotations, rendered DOM) 80% on the evaluated files (May 2024; adoption about 64%).
- **Key points.** The cleanest measured returns anywhere are on bounded, repeated work; brute-force retries hit a ceiling (Airbnb: 50-100 attempts); "keep them apart, then combine" has a hard number (45%, 40-60%, 80%); the sample-tune-sweep loop is "every bug becomes a prompt rule".

### 2.8 WorkOS: Horizon

- **What they built.** An event-driven code factory: Linear and GitHub webhooks feed an orchestrator that manages sandbox lifecycles; a PM agent splits projects into issues; OpenCode runs in Cloudflare sandboxes with egress proxied through Workers; a merge triggers the next unblocked issue ([May 6, 2026](https://workos.com/blog/project-horizon)). Inspired by Ramp's Inspect and Stripe's Minions.
- **Orchestration and sandbox.** "It's important that this orchestration logic lives outside of the sandbox." Started on GitHub Codespaces, then moved to Cloudflare Containers with the Sandbox SDK for stronger, more explicit egress controls.
- **Admitted limits.** "A human is always in the loop when the agent hands off the pull request" and "humans are frequently the bottleneck".
- **Key points.** The orchestrator lives outside the sandbox; Codespaces was a stepping stone outgrown because agents need programmatic lifecycle and egress control.

### 2.9 OpenSearch: a harness-first SDLC

- **What they built.** Four agents: Atlas (knowledge base), Ralph (parallel development pipeline), Nitro (performance optimizer) and Sentinel (on-call, which executes only after human approval) ([May 14, 2026](https://opensearch.org/blog/harness-first-agentic-sdlc-how-opensearch-builds-software-using-its-own-search-engine/)).
- **Results.** Ralph verifies against a live local stack on every iteration. Nitro A/B-tests candidate fixes against a baseline: it rejected two candidates for regression and promoted one, with a 5% improvement in sort-plus-term query latency and 12% less garbage-collection time; three validated fixes in about six days.
- **Lessons they state.** "Never let the agent write its own quality gates"; "protect the context window with disposable subagents, and keep the real state on disk"; "capture every failure as a rule in the instruction file".
- **Key points.** Three rules in one post (verify outside the agent, state on disk, every bug becomes a rule).

### 2.10 StrongDM: the software factory

- **What they built.** A "non-interactive development" rule set: "Code must not be written by humans" and "Code must not be reviewed by humans" ([StrongDM](https://factory.strongdm.ai/), Feb 2026).
- **How verification works.** Agents gamed narrow tests ("return true is a great way to pass narrowly written tests"), so StrongDM moved to end-to-end scenarios stored outside the codebase like a holdout set, scored as probabilistic "satisfaction" against a Digital Twin Universe of cloned Okta, Jira, Slack and Google services.
- **The provocation.** "If you haven't spent at least $1,000 on tokens today per human engineer, your software factory has room for improvement."
- **Key points.** Holdout scenarios as a lie detector; the $1,000 line as the question to answer honestly with cost per merged feature ([Cost Economics](cost-economics.md)). A keynote critique, ["Why Software Factories Fail"](https://www.youtube.com/watch?v=Ib5GBkD555M) (Dex Horthy, AI Engineer channel), is the further viewing.

### 2.11 Datadog: golden paths for agents

- **What they built.** Guidance on adapting golden paths for autonomous agents ([Aug 25, 2026](https://www.datadoghq.com/blog/golden-paths-for-ai-agents/)): long-running agents need a durable execution pattern; "place deterministic controls between a probabilistic output and the resulting action"; the agent "can revise an output that fails these gates, but it can't override them or decide that its own work satisfies the release conditions".
- **Concrete rules.** Idempotency keys so repeats return the original result; retry budgets (for example revise and rerun tests three times); terminal states succeeded, failed, cancelled, expired, approval denied and escalated; a dispatch chain from signal through curated context, task identity and allowed capabilities to a recorded output.
- **Admitted failure.** Its own AI Gateway rolling deployment had a graceful shutdown period "too short for in-flight agent requests to complete".

## 4. Patterns across cases

1. **A deterministic layer around the agent.** Stripe's blueprints, Spotify's surrounding infrastructure, Airbnb's per-file state machine, Google's deterministic targeting, Shopify's Roast, WorkOS's external orchestrator, Datadog's gates and Block's Moneybot all keep ordering, side effects and budgets in code. The live disagreement is how far to go: Cursor found too much structure creates fragility, Weave's reference platform lets LangGraph nodes that are LLM calls [influence control flow](https://weaveintelligence.io/blog/what-is-an-agentic-engineering-platform), while an abstract for a KubeCon NA 2026 session (Nov 9, not yet delivered) describes an incident RCA system on [LangGraph and Temporal where "the LLM decides nothing about workflow progression"](https://events.linuxfoundation.org/kubecon-cloudnativecon-north-america/co-located-events/cncf-hosted-co-located-schedule/). A workable resolution: the controller owns order, side effects, retries and budgets; the agent owns the how inside one phase.
2. **Homegrown runners converge on durable execution.** Cursor's ECS system (about 90%) became Temporal (over 99%); Ramp's on-call agent uses Temporal to survive restarts and deploys; XY replaced a queue-and-polling orchestrator; Aient runs everything on Restate; Datadog's guidance prescribes a durable execution pattern for long-running agents, and the [Agent Reliability Score](https://platformengineering.org/blog/the-agent-reliability-score-what-your-ai-platform-must-guarantee-before-agents-go-live) says agent workloads are closer to long-running workflow engines than to model serving. Not everyone: Ramp's coding sessions use Durable Objects, Spotify uses Fleetshift, Stripe discloses nothing.
3. **Isolation is the permission model.** Devboxes (Stripe), Modal VMs (Ramp), Cloudflare sandboxes (WorkOS), Kubernetes pods with restricted tools (Spotify), isolated worktrees and disposable staging (Block). Agents inherit their operator's blast radius otherwise (the disputed Kiro report).
4. **Verification sits outside the agent.** Stop hooks and an LLM judge (Spotify), holdout scenarios (StrongDM), validators (Ramp rejected 40% of findings), "never let the agent write its own quality gates" (OpenSearch), statistical re-runs (Block), a hook that blocks a bypass (Intercom).
5. **Caps are written down and enforced in code.** Stripe: two CI rounds. Spotify's early loop: 10 turns and 3 retries. Airbnb: a ceiling near 50-100 attempts per file. Datadog: retry budgets with terminal states. Cost: model routing and weaker defaults (Uber, Coinbase), see [Cost Economics](cost-economics.md).
6. **Autonomy for reversible steps, humans for irreversible ones.** Block keeps merges and ticket closing human; Spotify's git tool never pushes; WorkOS has a human at PR hand-off; OpenSearch's Sentinel runs only after approval.
7. **Bounded scope and foundations decide the outcome.** Migrations show the best measured returns; Intercom's 2x and Spotify's gains came on mature CI/CD, tests and consistent codebases; Spotify's dataset migration stalled where tests did not exist; KubeStellar needed 91% coverage and stable tests first.
8. **The bottleneck moves to verification and review.** Spotify: 76% more PRs to review; WorkOS: humans are the bottleneck; the research on review agents shows good but not lights-off performance (see [Productivity Evidence](productivity-evidence.md)).
9. **Every failure becomes a rule.** Airbnb's sample-tune-sweep, OpenSearch's instruction-file rule, KubeStellar's "why didn't you catch this?", WorkOS agents mining session logs, Ramp's detour hooks after blocking hooks backfired.
10. **Failures that look like success.** Spotify's CI-green-but-wrong PRs and a dependency upgrade that passed checks; StrongDM's "return true"; Anthropic's compiler where tests passed and the job was not done; Block's one green run proving little.

## Gap-fill additions (2026-10-12)

- **Block's orchestrator model, from the vendor's side (2026-10-08).** Section 2.6 covers BuilderBot and Moneybot; [How Block orchestrates Claude Fable across thousands of pull requests](https://claude.com/resources/articles/how-block-orchestrates-claude-fable-across-thousands-of-pull-requests) (vendor interview with Block's lead for AI capabilities) adds the orchestrator's model role. The strongest model does "the higher-level design work: data models, API specs, algorithms" and "directs up to dozens of smaller, more cost-effective models like Opus or Sonnet" to make file edits and run tests; early results show it "using frontier tokens for complex, upfront planning before driving a higher percentage of tokens to smaller worker models, without a drop in quality" (a vendor claim, not measured here). Scale: "In any given migration, we might merge a thousand pull requests orchestrated by Fable."
- **Humans on merge and deploy, cheap model-free checks (patterns 4 and 6).** The same interview confirms pattern 6: "We always leave merges to main and deploys to production up to people, along with related changes like feature flags", and two humans approve the deploy. For pattern 4, "A lot of our security guardrails are really cheap, efficient checks that run without the model needing to be involved... Sometimes it's even a regex." It is the fresh public example of an LLM as orchestrator beside Cursor's planner, worker and judge hierarchy in section 2.4; cite it as a vendor interview, not as evidence that an LLM orchestrator is safe.
- **Replit's runner moved from Temporal to Restate, per the vendor's case study.** Pattern 2 says homegrown runners converge on durable execution; the other direction also happens between engines. [Replit Agent switched to Restate for faster durable execution, cost efficiency, and BYOC](https://restate.dev/use-cases/replit) (vendor, undated) says Replit "initially used Temporal for this, but switched to Restate for three main reasons", and that "Replit Agent executes thousands of fast, inline durable steps per turn". Vendor-written; details in [Engine Profiles](engine-profiles.md).
