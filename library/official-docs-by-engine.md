# Official Docs by Engine

> **How this directory was built**
> All entries were collected in October 2026 across 31 topic areas; every URL was opened, and numbers, versions and dates that could not be found on the page were removed. Links checked 2026-10-12. Pages are grouped by the vendor or project that publishes them.

## If you only read one page per engine

- **Temporal**: [Temporal Workflow Definition (determinism and constraints)](https://docs.temporal.io/workflow-definition). The authoritative statement of the determinism rule: replayed workflow code must emit the same Commands in the same order, and "To handle non-deterministic operations like API calls, LLM/AI invocations, database queries, and other external interactions, put them in Activities."
- **Restate**: [Integrating Restate with LLM / Agent SDKs](https://docs.restate.dev/ai/sdk-integrations/integration-guide). A replay-safety checklist for agent SDKs: wrap every model call in ctx.run with capped retries ("to prevent infinite retries and high LLM costs"), disable streaming and SDK-native parallel tool calls, and persist SDK-generated IDs and timestamps. Wrapping the whole agent in one ctx.run is "coarse-grained fault tolerance", which treats the agent as one recoverable step. It shows the collision with LLMs is the same on every engine.
- **Inngest**: [Durable Workflows / How Inngest Functions Run](https://www.inngest.com/docs/durable-execution/durable-workflows). States the model plainly: a run resumes by replaying the handler and returning saved step results keyed by a hash of the step ID, and "Code outside a step can run again each time the handler replays." That sentence is Inngest's version of the determinism rule.
- **DBOS**: [DBOS Architecture](https://docs.dbos.dev/architecture). The engine in one page: a library that checkpoints workflow inputs and step outputs to Postgres, with one database write per step plus two per workflow and a vendor-stated sustained ">40K workflows or steps per second" on a single Postgres. It also says "The workflow function must be deterministic" and "Steps should be idempotent", so the discipline is the same; what changes is that you run no separate server.
- **Hatchet**: [Durable Tasks and Durable Execution (Hatchet v1 docs)](https://docs.hatchet.run/v1/durable-tasks). Durable tasks "must only either call methods on the durable context or spawn children", each completion writes a checkpoint to a durable event log, and "the code between checkpoints must be deterministic". Replay "doesn't re-execute completed operations, but it does re-run the code path that led to each checkpoint", which shows how strict the rule is when the engine is a task queue.
- **Trigger.dev**: [How Trigger.dev works: the Checkpoint-Resume System](https://trigger.dev/docs/how-it-works). The non-replay option: it snapshots the whole process with CRIU when a task waits on a subtask or a long timer, releases compute and restores the process later, so there are no determinism rules. A wait shorter than 60 seconds does not checkpoint, and durable execution means the Checkpoint-Resume System "combined with idempotency keys".
- **Vercel Workflow**: [Workflow Pricing and Limits (Vercel docs)](https://vercel.com/docs/workflows/pricing). Per-event pricing and the limits that matter for long agent turns: 50,000 events a month included on Hobby, $0.02 per 1K events, a maximum workflow replay duration of 240 seconds, and slower replay beyond 2,000 events or 1 GB of entity storage. The lesson is to keep long agent turns out of the workflow event log and use child workflows.
- **Cloudflare Workflows and Agents**: [Rules of Workflows (Cloudflare Workflows)](https://developers.cloudflare.com/workflows/build/rules-of-workflows/). The determinism contract as a short rule list: step names act as the cache key of the Workflow, "Workflows may hibernate and lose all in-memory state", and logic outside steps "may be duplicated" if the engine restarts. Name steps deterministically and keep state inside steps.
- **Resonate**: [Resonate: distributed async await](https://docs.resonatehq.io/). The only page in the set, and enough to place it: a distributed async/await protocol built on durable promises, one Apache 2.0 server binary, state in your own Postgres. Its cost claim ("~$80K/year on hosted alternatives" versus "under $100/year") is a vendor claim; treat it as marketing.
- **AWS Step Functions and Bedrock AgentCore**: [Durable functions or Step Functions](https://docs.aws.amazon.com/lambda/latest/dg/durable-step-functions.html). AWS's own decision guide: Lambda durable functions (standard programming languages, inside Lambda) versus Step Functions (graph DSL, "220+ AWS services, 16k APIs"), with a hybrid of durable functions for application logic and Step Functions for cross-service coordination. A rare vendor page written as a tradeoff, so place the third-party engines beside it.
- **Azure Durable Functions, Durable Task, Microsoft Agent Framework**: [Durable Task for AI agents](https://learn.microsoft.com/en-us/azure/durable-task/sdks/durable-task-for-ai-agents). A cost-led case for durable execution: the runtime "checkpoints every state transition (LLM responses, tool call results, control flow decisions)", so completed LLM calls are not repeated after a crash. Its comparison table rates Agent Framework workflows as long-running "Via developer-controlled checkpointing" with failure recovery "Manual".
- **Dapr**: [Dapr Workflow features and concepts (replay, determinism)](https://docs.dapr.io/developing-applications/building-blocks/workflow/workflow-features-concepts/). Dapr Workflows are event-sourced ("an append-only log of history events"): the workflow function re-runs from the start and completed tasks return stored results, so the code must be deterministic. The page warns against infinite loops and scheduling thousands of tasks, and points to continue-as-new. Read it if your platform team already runs Dapr.
- **CrewAI**: [CrewAI Checkpointing](https://docs.crewai.com/v1.15.27/en/concepts/checkpointing). Checkpoints are triggered by events: the default is one per completed task (task_completed) and llm_call_completed is available for finer recovery; restoring skips completed tasks and forks start a new lineage. Know which granularity you are buying: the default recovers per task, not per model call.
- **OpenAI Agents SDK**: [OpenAI Agents SDK: Running agents (durable execution integrations)](https://openai.github.io/openai-agents-python/running_agents/). For runs that span long waits, retries or restarts the SDK itself points to four durable integrations: Dapr, Temporal, Restate and DBOS. The Restate integration "requires Restate's single-binary runtime" and the DBOS one "requires only a SQLite or Postgres database", which is the operations tradeoff in one line.
- **Google ADK**: [Google ADK: Resume stopped agents](https://adk.dev/runtime/resume/). With ResumabilityConfig(is_resumable=True), ADK records completed events and resumes an invocation by invocation_id, and Loop agents restore their position from current_sub_agent and times_looped. The line to keep: tools "are run at least once, and may run more than once when resuming".
- **Pydantic AI**: [Pydantic AI: Durable Execution overview](https://pydantic.dev/docs/ai/capabilities/durable_execution/overview/). A neutral index: "Pydantic AI supports eight durable execution solutions, plus a builder for any other engine", five co-maintained with the vendors (Temporal, DBOS, Prefect, Restate, AWS Lambda) and three external (Kitaru, Apache Airflow, Absurd). A fast way to see which engines have framework-level integrations.
- **Apache Airflow**: [Durable execution (common.ai provider docs)](https://airflow.apache.org/docs/apache-airflow-providers-common-ai/stable/durable_execution.html). durable=True on AgentOperator caches each LLM response and tool result under a fingerprint of the request, replays them on retry, and discards stale entries when anything about the agent changed. The catch is stated plainly: "Durable execution only helps when the task has retries configured. Without retries there is nothing to replay."
- **Prefect**: [Caching (Prefect docs)](https://docs.prefect.io/v3/concepts/caching). The default cache key is the task's inputs, its code definition and the prevailing flow run ID, and "Caching requires result persistence, which is off by default" (enable it with PREFECT_RESULTS_PERSIST_BY_DEFAULT=true). Those two defaults decide whether a retry pays twice.
- **Dagster**: [Dagster 1.13: AI Skills, Partitioned Asset Checks, Virtual Assets & 20+ New Components](https://dagster.io/blog/dagster-1-13-octopuss-garden). The only page in the set, and a useful negative: Dagster's AI story is coding agents authoring Dagster projects (an open skills repository and structured dg CLI commands), not running agents inside Dagster.
- **Argo Workflows**: [Step Level Memoization (Argo Workflows docs)](https://argo-workflows.readthedocs.io/en/latest/memoization/). Memoization stores template outputs in labelled ConfigMaps under a user-specified key, "In version 3.5 or later all steps can be memoized", and it is designed for "pure" steps (workflows "won't enforce this on you"). The "New features in v4.1" page lists no AI or agent features.
- **Kestra**: [Kestra 2.0: A New Engine, Workers Anywhere, and Flows as Agent Tools](https://kestra.io/blogs/release-2-0). Workers connect over "a single outbound gRPC stream", the queue is "independent of the database now", and an MCP Tool Trigger makes any flow callable by an agent (OSS, EE and Cloud), while the AI Copilot agentic loop and action-based RBAC are EE and Cloud only.
- **Flyte**: [Flyte 2 Is Generally Available: The Durable, Open-Source AI Runtime](https://www.union.ai/blog-post/flyte-2-is-generally-available-the-durable-open-source-ai-runtime). A ground-up rebuild that drops the static compiled graph for plain async Python, with a replay log for logic failures and infrastructure-aware retries that change resources after OOMs or preemptions. Its framing: "most of what actually breaks a long running AI workload isn't a bug, it's an infrastructure failure".

## Restate

It is the clearest place to see retry settings turn into a bill.
